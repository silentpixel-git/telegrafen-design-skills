Suggested end-to-end workflow

Recommendation

Seven steps from brief to final QA, each with an example prompt to copy and adapt. Replace the bracketed details with your own. Use one skill per prompt.

    1. Select a Figma frame and confirm the brief

      Before you design · No skill needed

      Know the user task, the primary action and the target sizes. Look at how other products solve the same task, for example on Mobbin, and borrow patterns, not visuals. Select the frame the new work should sit beside.

      Example prompt

      Help me sharpen the brief for a [screen or flow] that helps customers [user task] before we design anything. I’ve attached reference screens from Mobbin showing how other apps solve similar tasks. Summarise the patterns worth borrowing and the ones to avoid. Then list the user task, the primary action, the target sizes and any open questions. Use the references for patterns only, don’t copy their visuals, and don’t create anything in Figma yet.

    2. Generate one small, scoped view

      Mockups · Build & Iterate

      Ask for one view, not a whole flow. Expect questions about material unknowns and a Draft status of READY TO ITERATE, NEEDS CHANGES or BLOCKED.

      Example prompt

      /telegrafen-design-mockups. Use Build & Iterate. Design one [desktop or mobile] view that helps customers [user task]. Explain the primary customer action, use verified Telegrafen assets, place the new frame beside the selected frame, and ask about material unknowns.

    3. Rewrite or QA the customer-facing copy

      UX Writing · Rewrite or QA

      Use a separate prompt. QA is read-only unless you ask to “QA and fix” or “update”.

      Example prompt

      /telegrafen-ux-writing. Rewrite the copy in the selected frame for [user task]. Use du for the customer and vi for Telenor, sentence case and specific actions. Do not invent prices, eligibility or promises; mark missing facts for clarification.

    4. Run production and WCAG checks

      Mockups · Review & Finalize

      Runs the production and WCAG 2.2 AA design gates. Applies fixes only within the authorised scope and reports unrelated issues.

      Example prompt

      /telegrafen-design-mockups. Review & Finalize the selected frame. Inspect actual provenance/bindings, responsive states, accessibility and visual polish. Correct only authorised defects and report production/WCAG gates.

    5. Critique hierarchy, quality and brand

      Visual Design · Review

      Read-only. Findings are ranked Critical, Important or Polish, with Preserve decisions so good work survives rework.

      Example prompt

      /telegrafen-visual-design. Review the selected screen, read-only. Identify the five highest-impact findings for hierarchy, spacing, typography, composition, and premium Telenor expression. State what to preserve.

    6. Apply only the accepted recommendations

      Visual Design · Apply

      Implements accepted findings in a revision beside the original, returns a ledger (Implemented, Preserved, Blocked, Dismissed by user), then runs Mockup production QA and Visual acceptance QA.

      Example prompt

      /telegrafen-visual-design. Apply only accepted findings 1, 2 and 4; preserve confirmed content and interactions. Provide an implementation ledger and validation.

    7. Hand off new reusable components

      Components · separate handoff

      If the design needs a new reusable component, send a separate Components prompt. Do not use Mockups to build component APIs.

      Example prompt

      /telegrafen-design-components. Use Build & Iterate. The design needs a reusable [component] for [user need]. Inspect the closest approved Telegrafen components first, then ask me one question at a time about purpose, anatomy, content, states and behaviour. Summarise the contract and wait for my confirmation before building.

    Choosing the right mode

    Review modes are not interchangeable

    Mockups Review & Finalize inspects the full scope, corrects defects in the requested area and runs the production and WCAG 2.2 AA gates. Components Review & QA, Visual Design Review and UX Writing QA are read-only: they report findings and change nothing unless you explicitly authorise edits.

    Source rules everyone should know

    These come from the SKILL.md files. Every prompt should follow them.

    1. One skill per prompt. Only the first Figma Resources skill mentioned in a prompt is reliably invoked. Use separate prompts and explicit handoffs.
    2. Live Telegrafen is the authority. Verify actual component instances, icon, style and variable bindings, and provenance. Visual resemblance does not prove compliance.
    3. No guessing on material decisions. Inspect the system first, then ask about unresolved user needs, purpose, behaviour, content or constraints. Components has a stricter interview-and-confirmation gate.
    4. Mockups assembles screens. It hands off reusable component anatomy, properties, variants, states or QA to Components.
    5. New frames are siblings, placed to the right. Mockups creates new independent design frames beside the anchor in the same Section (or Page), never inside the selected object.
    6. Production assets by default. Beta or experimental assets need your consent. Preserve existing work, content and accepted design decisions.
    7. Dark surfaces are local dark-mode contexts. Verify nested colours, states and controls. In dark contexts, Button Neutral is Off. Components goes further: never enable Neutral on a Button.
    8. No invented facts or fake PASS. Do not invent commercial facts or claim a verified PASS without evidence. Missing necessary provenance or access is BLOCKED.

    Practical design tips

    • Task first. Prioritise the user task and one clear primary action over decorative effects. Avoid unnecessary cards and repeated containment; consider open lists and grids.
    • Real styles and tokens. Use published typography styles and semantic colour tokens, not visual copies or hard-coded approximations.
    • Stress the design. Check component states and interactive affordances, light and dark contexts, resizing, long labels and wrapped text.
    • UX Writing. Clear, calm Norwegian Bokmål. du for the customer and vi for Telenor, sentence case, specific actions. Never invent prices, eligibility or promises.
    • QA. Give evidence-backed status, scope and remaining blocks. An attractive output alone is not a PASS.
